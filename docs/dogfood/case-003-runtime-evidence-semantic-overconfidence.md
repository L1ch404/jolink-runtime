# Case-003：Runtime Evidence 导致过度自信——一次字段语义误读

> **数据说明**
>
> 本文来自一次真实 dogfood 排查，但其中的机构名称、机构 ID、地点、
> 数据数量、方法名、权限字段名和 SQL 别名均已替换为虚构或泛化内容。
> 匿名化不改变原始问题的证据关系、推理过程和最终结论。

## 一、问题背景

业务现象如下：

> 在任务列表中筛选“西南区域分公司”，结果里却出现了大量显示为
> “数字产品研发中心（筹）”的任务。

为了定位问题，使用相同模型、相同代码版本和基本相同的问题描述，
分别开启了多个 Agent 窗口进行分析。

## 二、不同 Agent 的分析结果

### 窗口 A：真正使用 joLink 进行运行时观察

Agent 使用 joLink 在 `queryTaskList` 中设置断点，并读取了请求参数和
局部变量。

运行时观察到：

```text
body.orgIds = ["7301"]
result.size = 12
```

12 条结果中：

```text
11 条 orgName = 数字产品研发中心（筹）
1 条 orgName = 西南区域分公司
```

这证明了：

1. 西南区域分公司的机构 ID `7301` 已经正确传入业务方法；
2. 返回结果中的 `orgName` 与筛选机构名称存在明显差异。

Agent 随后追踪到 `createWorkItem` 中的：

```sql
selectFirstOrgByUserId
ORDER BY membership.id
LIMIT 1
```

它认为员工发生调岗后，该查询可能取到旧部门，从而在创建任务时写入
错误的 `organization_id`。

由此得出结论：

> 任务的机构数据在创建时已经写错，导致西南区域分公司的筛选错误命中
> 了其他部门的任务。

### 窗口 B：完全静态分析

另一个未使用 joLink 的窗口，通过对比相似接口发现：

```text
queryMessageList 和 exportTasks 有 departmentScopeFilter
queryTaskList 没有 departmentScopeFilter
```

因此它判断 `queryTaskList` 缺少数据权限隔离，并提出了增加权限部门过滤
的修改方案。

这个问题确实存在，修复方案也有一定合理性，但它解决的是：

> 用户是否有权限查询某些部门的数据。

它没有直接解释：

> 为什么筛选西南区域分公司后，结果中的 `orgName` 显示为数字产品研发
> 中心。

因此，这个窗口发现了一个真实存在的相邻问题，但没有找到当前业务现象
的根因。

### 窗口 C：声明使用 joLink，但实际仍以静态分析为主

第三个窗口被明确告知可以使用 `jolink-runtime`，但它只调用了
`java_processes` 查看已有 Java 进程，没有继续 attach、设置断点或读取
变量。

严格来说，它只完成了：

```text
进程发现
```

并没有真正获得 Runtime Evidence。

但它通过静态阅读 SQL 注意到了两个不同的数据来源：

```sql
creator_org.display_name AS orgName
```

表示创建人的所属部门；而筛选条件使用的是：

```sql
task_org.organization_id IN ('7301')
```

表示任务实际包含的目标机构。

因此它提出了另一个解释：

> 筛选本身可能是正确的，只是返回的 `orgName` 显示的是任务创建人的
> 部门，而不是此次筛选命中的目标部门，造成了用户误解。

## 三、竞争性假设

此时出现了两个都能解释部分现象的假设。

### 假设 A：底层机构数据写错

```text
createWorkItem 查询到错误部门
→ organization_id 写错
→ 西南区域分公司的筛选错误命中任务
```

### 假设 B：筛选正确，但展示字段语义不同

```text
任务实际包含西南区域分公司的数据
→ organization_id=7301，因此被正确筛选出来
→ orgName 却显示创建人的部门
→ 用户误以为筛选出了其他部门的数据
```

仅凭 joLink 第一次返回的变量，无法区分这两个解释。

joLink 证明的是：

```text
请求参数确实是 7301
返回对象中的 orgName 确实是数字产品研发中心（筹）
```

但它没有证明：

```text
orgName 就是被筛选机构的名称
```

这正是窗口 A 推理过程中引入的未经验证的语义假设。

## 四、数据库验证

随后直接查询原始数据表，发现前 11 条任务的数据结构完全相同：

```text
organization_id = 2608，华北创新园区，共 4 条
organization_id = 7301，西南区域分公司，共 18 条
```

第 12 条任务为：

```text
organization_id = 7301，西南区域分公司，共 18 条
```

数据库结果说明：

1. 这些任务确实包含西南区域分公司的数据；
2. `organization_id=7301` 并不是错误写入；
3. 使用西南区域分公司进行筛选时，这些任务被查询出来是正确的；
4. 页面展示的“数字产品研发中心（筹）”来自创建人的部门，而不是筛选
   命中的目标部门。

至此，假设 B 得到验证。

## 五、最终根因

本次问题的直接原因是：

> `queryTaskList` 返回的 `orgName` 来自任务创建人的部门，但用户将其理解
> 为任务所包含或当前筛选命中的部门。

因此实际情况是：

```text
筛选逻辑正确
底层任务机构数据正确
orgName 的来源和字段命名具有误导性
```

用户看到“数字产品研发中心（筹）”后，以为西南区域分公司的筛选失效，
实际上该任务同时包含西南区域分公司的目标数据。

更准确的问题定性应当是：

> **展示字段的业务语义不清晰，而不是机构筛选错误。**

窗口 A 找到的 `selectFirstOrgByUserId ORDER BY membership.id LIMIT 1` 仍然
可能是一个真实的潜在问题，特别是在员工调岗场景下，但它没有在本次
数据中触发，因此不是当前现象的根因。

## 六、使用 joLink 的 Agent 为什么判断错了

窗口 A 的推理过程是：

```text
看到 orgName 与筛选条件不一致
→ 假设 orgName 代表筛选部门
→ 认定底层 organization_id 写错
→ 找到一个可能导致写错的代码问题
→ 将其直接认定为根因
```

它跳过了最关键的验证步骤：

```text
先查询原始表，确认 organization_id 是否真的写错
```

断点中看到的 `orgName` 是 API 返回对象中的展示字段，其来源是 SQL 中的：

```sql
creator_org.display_name
```

它代表创建人部门，而不是 `task_org.organization_id` 对应的目标部门。

因此，真正的错误不是 Runtime 数据不准确，而是 Agent 对 Runtime 数据的
业务语义理解错误。

## 七、为什么静态分析窗口反而找对了

第三个窗口没有获得真正的运行时证据，因此只能仔细追踪 SQL 中每个字段
的来源。

它注意到：

```text
筛选字段和展示字段来自不同的数据链路
```

即：

```text
task_org.organization_id
负责筛选任务范围

creator_org.display_name
负责展示创建人部门
```

由于没有被“我已经看到了实际变量”带来的信心影响，它反而更加谨慎地
检查了字段血缘，并发现了真正的问题。

这并不说明静态分析一定优于 Runtime，而是说明：

> **字段来源和业务语义无法仅靠变量值本身确定。**

## 八、这个 Case 对 joLink 的意义

这是一个很有价值的反例。

它证明 joLink 可以减少：

```text
执行状态的不确定性
```

例如确认：

- 参数是否真的传入；
- 实际返回了多少条数据；
- 当前变量具体是什么值；
- 程序走到了哪条执行路径。

但 joLink 不能自动消除：

```text
字段语义的不确定性
因果关系的不确定性
业务规则的不确定性
```

本次案例中：

```text
Runtime Evidence 是正确的
Agent 对 Evidence 的解释是错误的
```

甚至由于获得了真实运行数据，Agent 产生了更高的主观置信度：

> “我已经看到 `orgName` 不对了，所以数据一定写错了。”

这是一种典型的**证据诱发过度自信**。

## 九、核心教训

### 1. 运行时事实不等于业务语义

```text
观察到 orgName="数字产品研发中心（筹）"
```

只能证明该字段在当前对象中的值，不能证明它代表此次筛选的目标部门。

### 2. 发现可疑代码不等于找到当前根因

`selectFirstOrgByUserId` 的排序问题可能真实存在，但还需要证明它在当前
数据中实际发生。

### 3. Runtime Evidence 需要和字段血缘、数据库数据联合验证

完整证据链应当是：

```text
Runtime 观察请求参数和返回值
→ 静态追踪字段来源
→ 查询数据库原始数据
→ 比较竞争性假设
→ 最终确认根因
```

### 4. Agent 应明确区分事实、推断和结论

本次更正确的表达应该是：

```text
已观察事实：
orgIds=["7301"]，返回结果中的 orgName 大量为数字产品研发中心。

当前推断：
可能是底层 organization_id 写错；
也可能是 orgName 与筛选字段语义不同。

待验证：
查询原始 organization_id，并检查 orgName 的 SQL 来源。
```

而不应直接宣布：

```text
selectFirstOrgByUserId 就是根因。
```

## 十、最终总结

在这次排查中，joLink 成功提供了真实请求参数和返回对象，但 Agent 错误地
将展示字段 `orgName` 理解为筛选机构名称，因此把一个真实存在但未在当前
场景触发的代码问题误判为根因。另一个主要依赖静态分析的 Agent 通过追踪
SQL 字段来源，发现筛选字段与展示字段来自不同数据链路。数据库原始数据
最终证明筛选逻辑和机构数据均正确，真正的问题是展示字段的语义具有
误导性。

这个 Case 最重要的结论是：

> **Runtime Evidence 能告诉 Agent 程序实际发生了什么，但不能自动告诉它
> 这些数据在业务上意味着什么。**

进一步说：

> **joLink 减少的是执行不确定性；正确的根因判断还需要语义理解、竞争性
> 假设和验证闭环。**

这也为 joLink 后续的 Agent 使用规范提供了一个明确方向：

> **看到异常变量后，不要立即宣布根因；先检查字段来源和原始数据，区分
> “观察到的事实”与“对事实的解释”。**
